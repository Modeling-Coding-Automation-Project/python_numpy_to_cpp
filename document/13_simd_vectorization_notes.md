# テンプレート展開とSIMDの採用条件

調査日：2026-11-17

## 1. 結論

**テンプレート展開した積和算も、自動SIMD化できる。今回の複素行列積では、GCCがSIMD化の候補を認識したうえで、コストの見積りによって一部を見送っていた。** テンプレート展開という記述方法だけを理由に、SIMDを使えないわけではない。

追加調査では、疎行列積などに**テンプレート版だけがSIMDを使う例**も見つかった。for版・テンプレート版のどちらか一方が、常にSIMD化に適しているとは言えない。

| 確認したいこと | 結論 |
| --- | --- |
| どのような条件でSIMDを使うか | 対象CPUで命令を使用でき、計算の意味を保つ変換ができ、コンパイラが有利と判断した場合 |
| どのような積和算の並びが適しているか | 別々の出力を更新する、同じ形の独立した積和算。1個の和に順番に足す処理とは区別する |
| 本リポジトリのテンプレート展開はSIMD化されるか | 処理・型・次数・呼出し方で異なる。複素行列積にもSIMD化された部分と見送られた部分がある |
| 必ずSIMDを使うテンプレート展開方法はあるか | **移植可能なC++11の自動最適化だけでは保証できない。** 対象CPUを限定し、専用実装と生成コード検査を組み合わせる運用はできる |

本資料は、[前回の機械語調査](12_convergence_tolerance_tuning.md)を補足する。今回の作業は調査と記録であり、行列ライブラリの実装やビルドオプションは変更していない。

## 2. 「SIMDを使った」の意味

本資料では、**複数の浮動小数点成分を1命令で加減乗除すること**を判定対象とする。x86の`addps`・`mulpd`などが該当する。`addss`・`mulsd`はXMMレジスタを使っていても、演算する成分は1個なので、この意味でのSIMDには数えない。ベクトルレジスタによるコピーだけがあっても、積和算のSIMD化とは区別する。

また、SIMDとFMAは別の性質である。SIMDでも乗算と加算が別命令の場合があり、FMAでも1成分だけを処理する場合がある。本資料の既存追跡ではFMAは出現していない。

### 2.1 for文からの変換と、並んだ式からの変換

| 方式 | まとめる対象 | 記述例 |
| --- | --- | --- |
| ループのベクトル化 | 複数の反復で行う同型の計算 | `for (...) y[i] += a[i] * x;` |
| SLP（並んだスカラー式のベクトル化） | 近くにある、まとめて実行可能な同型の式 | `y[0] += a[0]*x; y[1] += a[1]*x; ...` |

テンプレート再帰がインライン展開されれば、後者の対象になり得る。for文の本体の中でもSLPは働くため、**for版にSIMDがあることだけでは、複数反復をまとめたとは判断できない。** 今回の複素行列積には、1要素の実部・虚部計算をまとめた例がある。[GCCのベクトル化とSLPの説明・例](https://gcc.gnu.org/projects/tree-ssa/vectorization.html)

## 3. SIMDを採用する条件・見送る条件

以下は一般的な判断条件である。各条件が、今回のすべての非SIMD箇所の直接原因だったという意味ではない。

| 条件 | SIMD化しやすい状況 | SIMD化しない、または不利になる状況 |
| --- | --- | --- |
| CPU・データ型 | 使用可能な命令が必要な型・演算に対応する | 対応命令がない、コンパイル対象の命令セットで許可されていない |
| 最適化設定 | 自動ベクトル化が有効 | 最適化無効、SLPなど該当する最適化を無効化 |
| データ依存 | 各出力の計算が独立 | 前の計算結果を次の計算で必要とする |
| メモリの重なり | 読む領域と書く領域の関係を解析できる | ポインタが重なる可能性があり、まとめて読むと意味が変わる |
| データ配置 | 隣り合う要素をまとめてロード・保存できる | 飛び飛びのアクセス、成分の並べ替えや詰め直しが多い |
| 制御・関数呼出し | 分岐を解決できる、演算本体が見える | 要素ごとに分岐する、関数呼出しの副作用が不明、`volatile`アクセスがある |
| 処理量・コスト | 準備・後処理より並列化の利益が大きい | 少量の処理、余り要素、追加チェック・並べ替え・レジスタ使用などの負担が大きい |

境界の整列、分岐、間接アクセスは、あるだけで常に不可能になるわけではない。非整列ロード、マスク、実行時の重なり検査などを利用できる場合もある。ただし、生成可能であることと、採算がよいと判断されることは別である。[LLVMのベクトル化条件・実行時検査の説明](https://llvm.org/docs/Vectorizers.html)

今回のGCC 15.2では、`-O2`にループとSLPの自動ベクトル化が含まれる。採否はコストモデルにも依存し、同じソースでもコンパイラの版・対象CPU・最適化設定によって変わる。実際の有効設定は`-Q --help=optimizers`で確認できる。[GCC 15.2の最適化オプション](https://gcc.gnu.org/onlinedocs/gcc-15.2.0/gcc/Optimize-Options.html)

## 4. 積和算の書き方による違い

### 4.1 別々の出力を更新する式

```cpp
y[0] += a[0] * x;
y[1] += a[1] * x;
y[2] += a[2] * x;
y[3] += a[3] * x;
```

`a`と`y`の重なりなどに問題がなければ、4本の独立した計算としてまとめられる。1個の出力に対する加算順序を変える必要がない点が利点である。この並びを手書きしたか、テンプレートで生成したかは本質的な違いではない。

例えば、既存の再帰テンプレートの書き方で、次のように生成できる。

```cpp
template <typename T, std::size_t N, std::size_t Index> struct Update {
  static inline void compute(const T (&a)[N], T x, T (&y)[N]) {
    y[Index] += a[Index] * x;
    Update<T, N, Index + 1>::compute(a, x, y);
  }
};

template <typename T, std::size_t N> struct Update<T, N, N> {
  static inline void compute(const T (&)[N], T, T (&)[N]) {}
};
```

これはSIMD化の候補を作る記述であり、SIMD化を指示する文法ではない。配列参照や`const`も、入力・出力が重ならないことを単独で保証するものではない。`inline`指定も、すべての呼出しが展開される保証にはならない。[GCCのinlineの説明](https://gcc.gnu.org/onlinedocs/gcc/Inline.html)

### 4.2 1個の和に順番に加算する式

```cpp
sum += a[0] * b[0];
sum += a[1] * b[1];
sum += a[2] * b[2];
sum += a[3] * b[3];
```

各加算が、直前の`sum`を必要とする。これを複数の部分和へ分けて最後にまとめると、浮動小数点の加算順序が変わり、丸め誤差も変わり得る。

一方で、乗算だけをまとめ、加算は元の順序で行う余地はある。そのため「1個の和への加算は絶対にSIMD化できない」とも言えない。実際にどの部分をまとめるかは、使用可能な命令とコンパイラの判断による。

本リポジトリでは精度・安定性も評価対象なので、SIMD化を目的として`-ffast-math`を一律に追加する方針にはしない。独立した複数出力をまとめる変更と、和の順番を変える変更は分けて評価する。

### 4.3 複素数の積和算

```cpp
output.real += a.real * x.real - a.imag * x.imag;
output.imag += a.real * x.imag + a.imag * x.real;
```

実部・虚部の計算には、同時に実行できる乗算や加算がある。ただし、そのために成分の複製・並べ替えや、結果に使わない成分の計算が増える場合がある。この負担を含めた判断によって、SIMD版を作れる場合でもスカラー版が選ばれる。

### 4.4 小さなコードでの実測例

上記の違いを確かめるため、GCC 15.2.0・x86-64・C++11・`-O2`で小さな関数をビルドした。次は**関数内の静的な四則命令の箇所数**であり、後述するソルバーの動的実行回数とは別の測定である。

| 記述・条件 | float | double |
| --- | --- | --- |
| 独立4出力、値渡しの固定配列構造体、直書き | packed乗算1＋加算1 | packed乗算2＋加算2 |
| 同じ値渡し・計算をテンプレート再帰で生成 | packed乗算1＋加算1 | packed乗算2＋加算2 |
| 同じ計算を2要素または4要素ずつのテンプレート再帰で生成 | packed乗算1＋加算1 | packed乗算2＋加算2 |
| 通常のポインタ引数から逐次読み書きする4出力、直書き／TMP | scalar乗算4＋加算4 | scalar乗算4＋加算4 |
| 1個の和への順序を保った加算、直書き／TMP | scalar乗算4＋加算4 | scalar乗算4＋加算4 |
| 値渡しの複素数1要素の積和算 | packed乗算2＋減算1＋加算2 | packed乗算2＋減算1＋加算2 |

SLPを無効にした対照ビルドでは、表のpacked四則演算はすべてスカラー演算になった。この小例からも、テンプレート展開後のコードがSLPの対象になることを確認できる。

値渡し版では別々の局所配列となり、ポインタ版とはメモリの重なりの条件や引数の受渡し方法も異なる。**この比較はSIMDが生成される例の確認であり、APIを値渡しに変更すると速くなる、という提案ではない。** 2要素・4要素のブロック化も、この例では同じ算術命令になっただけで、最適なブロック幅を確立したものではない。

入力64組をfloat/doubleで検証し、各記述と基準式の結果がbit単位で一致することも確認した。[ソース・機械語・再実行手順](../test_vs/algorithm_improvements/results/simd_vectorization_patterns/README.md)を保存した。速度・RAMはこの小例では測定していない。

## 5. 本リポジトリで確認した採用・不採用

対象は主に[GMRES周辺のテンプレート処理](../base_matrix/base_matrix_gmres.hpp)と[数値計算補助処理](../base_matrix/base_matrix_numerical.hpp)である。最適化の採否はテンプレート名に固定された属性ではないため、型・次数・呼出し条件を添えて結果を示す。

### 5.1 比較条件と判定範囲

既存の命令追跡は、GCC 15.2.0、Linux x86-64、C++11、`-O2 -Wall -Wextra -Werror`を使用した。`-march=native`・`-ffast-math`は指定していない。TMP版とfor版の違いは`BASE_MATRIX_USE_FOR_LOOP_OPERATION_`のみである。

対象本体は`6b1d627edf2de6e3e56deca59b83b37e942a97aa`。本資料作成時の`e89056c`との`base_matrix`差分はGMRES・固有値ソルバーの既定許容誤差と説明コメントであり、ここで調べる`GmresOperation`・`Numerical`などの実装本体は同じである。GMRESの追跡では相対・絶対許容誤差を明示的に0へ設定しているため、新しい既定許容誤差での命令数を示すものではない。

8/16次、float/double、実数/複素数を対象とし、`active_size=N`。専用の呼出し境界内とその呼出し先を追跡した。全20組でTMP/forの結果はbit単位で一致した。[測定条件・全40追跡の原記録](../test_vs/algorithm_improvements/results/convergence_tolerance_tuning/instruction_counts/README.md)

### 5.2 実行された四則演算の比較

表の数値は**1呼出しで実行した浮動小数点四則命令数**である。静的な命令の箇所数や、処理時間ではない。

| 対象 | 型・次数 | TMP版 | for版 | SIMDの確認結果 |
| --- | --- | ---: | ---: | --- |
| `GmresOperation::multiply`、密行列 | 実数float/double、8次 | 128 | 128 | 両版とも四則演算はスカラー |
| 同上 | 実数float/double、16次 | 512 | 512 | 両版とも四則演算はスカラー |
| 同上 | 複素float/double、8次 | 512 | 320 | TMP版はスカラー、for版はpacked演算あり |
| 同上 | 複素float/double、16次 | 2039 | 1280 | TMP版にもpacked加算9回あり。for版はpacked演算を広く使用 |
| `Numerical::norm` | 実数float/double、8 / 16次 | 41 / 65 | 41 / 65 | 両版とも四則演算はスカラー |
| 同上 | 複素float/double、8 / 16次 | 65 / 113 | 65 / 113 | 両版とも四則演算はスカラー |
| `GmresSolver::solve`全体 | 実数double、8 / 16次 | 3981 / 22757 | 3981 / 22757 | 両版ともpacked演算を含む |

実数floatのGMRESも、両版ともpacked演算を含み、命令数は8次3689、16次20573で一致した。**「for版だけがSIMDを使い、TMP版は一切使わない」という分類は正しくない。** また、ソルバー全体にSIMDがあることを、その内部のすべての積和算がSIMD化されたという意味にはしない。

複素double・8次のfor版では、1要素につき`mulpd`2回、`subpd`1回、`addpd`2回が実行される。ループは1回につき複素数1要素分進むので、これは主に**1個の複素積和算の内部をまとめたSIMD化**である。複数行を一括処理したという意味ではない。

この例の命令数はTMP512回、for320回だが、全laneの演算数はTMP512、for640となる。SIMD化には使わないlaneの計算もあり、命令数の削減と数学的な演算数の削減は一致しない。命令数だけから、実行時間やピークRAMの大小も決められない。

### 5.3 GCCはテンプレート展開を認識しているか

最適化診断とSLPの内部ダンプでは、次の例を確認した。

| 診断対象 | GCCのコスト見積り | 判断 |
| --- | --- | --- |
| TMP：`DenseMultiply::Row<Complex<double>,16,15,8,true>`の複素積和候補 | vector 332 / scalar 224 | 候補の解析に成功したが、不利として見送り |
| 同じTMPヘルパー内の加算部分 | vector 40 / scalar 72 | 一部をSLP化 |
| for：複素double・8次の積和部分 | vector 164 / scalar 224 | SLP化 |

ここでいうコストは**GCC内部の見積り値であり、CPUのサイクル数でも測定時間でもない。** 表の16次と8次は異なる関数・最適化文脈なので、この数値をそのまま関数全体の速度比較には使わない。

for版に`-fno-tree-slp-vectorize`を追加すると、調べた複素double・8次の関数からpacked四則演算が消えた。したがって、今回のfor版の利点も「for文があるから」だけでは説明できず、SLPの判断が関わっている。

証跡・再生成手順は[SLP診断の記録](../test_vs/algorithm_improvements/results/simd_vectorization_notes/README.md)を参照。巨大な内部ダンプ全体ではなく、関数境界と対象候補を識別できる抜粋を保存している。

### 5.4 その他のテンプレート処理の確認

密行列積以外も確認するため、現在のHEAD `e89056c`で9種類の入口を追加調査した。実数float/double、8/16次、正方行列、`active_size=N`を使用した。疎行列は各行に2要素を持つ固定CSR配置であり、あらゆる疎構造を代表するものではない。

次は入口関数と、その直接呼出しをたどって到達する関数群に含まれる**packed四則命令の静的な箇所数**。セルは **TMP / for** の順で、0はその条件の関数群にpacked四則命令がなかったことを表す。実行した経路・回数の計測ではない。

| 入口・対応するテンプレート処理 | float・8次 | float・16次 | double・8/16次 |
| --- | ---: | ---: | ---: |
| 疎行列積：`SparseMultiply` | **8 / 0** | **16 / 0** | 0 / 0 |
| 密行列の転置積：`DenseTransposeMultiply` | 0 / 0 | 0 / 0 | 0 / 0 |
| 疎行列の転置積：`SparseTransposeMultiply` | **8 / 0** | **16 / 0** | 0 / 0 |
| 密行列の正規方程式生成：`DenseNormalEquations` | 0 / 0 | 0 / 0 | 0 / 0 |
| 疎行列の正規方程式生成：`SparseNormalEquations` | 0 / 0 | 0 / 0 | 0 / 0 |
| 密行列の残差計算：`DenseNormalResidual`と`Numerical::norm` | **32 / 0** | **16 / 0** | 0 / 0 |
| 疎行列の残差計算：`SparseNormalResidual`と`Numerical::norm` | 0 / 0 | 0 / 0 | 0 / 0 |
| `NormalOperator`の密行列版：`DenseNormalProduct`など | **0 / 2** | **0 / 2** | **0 / 2** |
| `NormalOperator`の疎行列版：`SparseNormalProduct`など | **24 / 0** | 0 / 0 | 0 / 0 |

この追加調査には、**TMP版がSIMDを使い、for版では使わない例もある。** 疎行列積ではテンプレート引数によって要素位置が固定されるが、今回の差をその効果だけに切り分けたわけではない。また、疎行列の`NormalOperator`ではfloat・8次で採用され、16次では採用されなかった。単に「実数だから」「疎行列だから」「次数が大きいから」と分類できないことが分かる。

9入口×2型×2次数の36組について、TMP/forの全出力が16進表現で一致した。独立した数値精度試験や時間・RAMの測定は追加していない。[入口とヘルパーの対応・全集計・再実行手順](../test_vs/algorithm_improvements/results/simd_helper_map/README.md)を参照。

`VectorSubspace`・`ZeroNormalEquations`のクリア／コピーや、`Numerical::VectorNorm::ScaleLoop`の比較は、浮動小数点四則演算のSIMD採否とは別に扱う。クリア／コピーのベクトル命令が存在しても、上表には加算しない。`VectorNorm::SquaredSumLoop`については5.2のnorm全体の追跡が対応する。

これらは、専用の入口関数から呼んだ場合の結果である。同じヘルパーでも、実ソルバー内へインライン化した場合に同じ命令列になるとは限らない。部分サイズ、別の次数・CSR配置、追加9入口の複素数版、他の行列演算クラスの全経路、マイコン向けの生成コードは**未確認**であり、「SIMD不採用」と判定したものではない。

## 6. SIMD化されやすいテンプレート展開を設計できるか

**設計候補は作れるが、「この書き方なら必ずSIMD」という一般則にはできない。** 本リポジトリで試す価値があるのは、次のような方向である。

1. 別々の出力に対する2〜4本などの積和算を、近くにまとめる。各出力については元の加算順序を保つ。
2. 全体を一度に大きく展開する方式と、小さな単位で展開する方式を比較する。コード量、インライン化範囲、途中値の保存量も調べる。
3. 入出力のメモリ配置を明確にし、不要な成分の詰め直しを減らす。配列を追加して詰め直す方法は、RAMと変換時間も含めて評価する。
4. 現在の`FullSize`のように、全要素処理と部分処理の分岐を整理する。ただし、部分処理を切り捨てたり、実際には保証されないメモリ非重複を仮定したりしない。

この方針であっても、型、次数、インライン展開先、コンパイラの版が変われば採否は変わる。`base_matrix_matrix.hpp`や`base_matrix_compiled_sparse_operation.hpp`の全特殊化、QR・LU・Cholesky・固有値ソルバーの全経路について、今回の密行列積の結果を一般化することはできない。

## 7. 「必ずSIMD」をどこまで保証できるか

| 方法 | できること | 保証の限界 |
| --- | --- | --- |
| 通常のC++11＋テンプレート展開 | 自動SIMD化しやすい式を生成する | 命令セット・最適化判断に依存。必須命令は指定できない |
| ベクトル化オプション・pragma | 最適化を有効にする、依存関係の情報を与える | 対応CPUや変換可能性などの制約をなくすものではない |
| GCCのベクトル型拡張 | 複数成分の演算を明示する | 対象で未対応なら、狭い型やスカラーへ分解され得る |
| CPU専用intrinsics | 対象命令セットのベクトル演算を明示する | 移植性に制約。不要計算の削除などもあるので最終命令列を確認する |
| CPU専用アセンブリ＋生成物の検査 | 固定した環境で特定命令を実装・検証する | CPU依存。該当経路が実行される入力条件も別途必要 |

`#pragma GCC ivdep`は、ループ反復間にSIMD化を妨げる依存がないことをプログラマーが宣言するものなので、その前提が正しい場合に限って使う。[GCCのループpragma](https://gcc.gnu.org/onlinedocs/gcc-15.2.0/gcc/Loop-Specific-Pragmas.html)

GCCの`vector_size`も、CPUが指定サイズに対応しなければ、より狭い演算へ分解される仕様である。ベクトル型を使ったという事実だけでは、必ずSIMD命令になる保証はできない。[GCCのベクトル拡張](https://gcc.gnu.org/onlinedocs/gcc-15.2.0/gcc/Vector-Extensions.html)

対象CPUを限定できるなら、テンプレートの特殊化から専用intrinsicsを呼ぶ構成は考えられる。その場合、SIMDを指定しているのはテンプレート展開自体ではなく、専用の演算実装である。例えばx86用の組込み関数は、対応するコンパイル対象・オプションを前提とする。[GCCのx86組込み関数](https://gcc.gnu.org/onlinedocs/gcc-15.2.0/gcc/x86-Built-in-Functions.html)

実用上の保証は、**対象CPU・コンパイラ・オプション・型・次数・呼出し方を固定し、生成コードを継続検査すること**になる。最終実行ファイルの対象区間に期待するpacked演算があるかを調べ、必要なら実行経路も確認する。コンパイラ更新時には再検査する。

## 8. 本リポジトリでの採用判断

組み込み対象では、まず実際のCPUに必要なSIMDがあるかを確認する。整数用のSIMD機能があることと、float/doubleの行列演算を並列化できることも同一視しない。

通常のC++11実装とfor版の選択肢を維持し、対象CPUごとに次を比較する運用が適している。

1. `-fopt-info-vec-all`などで、認識・見送り理由を確認する。
2. 最終生成物を逆アセンブルし、四則演算、並べ替え、ロード・保存、呼出しを確認する。診断に「vectorized」とあるだけで目的の積和算が変わったと判断しない。
3. 同じ入力・パラメータで、数値精度と収束、実行時間、スタックを含むピークRAMを測る。命令数の少なさだけで採用しない。
4. SIMDを明示する専用実装を導入する場合も、固定メモリ・C++11・確定した反復上限などの既存条件を維持する。除算をベクトル化する場合は、使用する各成分の分母保護も維持する。

今回のx86-64の結果は、マイコンでの速度やRAMを保証するものではない。SIMDが生成されるかを確かめる調査と、実機で採用するかを決める性能評価を、両方の根拠を残して進める。
