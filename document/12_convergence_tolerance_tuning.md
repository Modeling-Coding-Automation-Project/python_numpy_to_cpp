# 許容誤差の既定値選定とテンプレート展開の検証

調査・更新日：2026-11-17

## 1. 今回の結論とC++への反映

**機械イプシロン由来の値から固定値へ変更すると、良くなる場合と悪くなる場合の両方がある。今回は全ケースの無悪化ではなく、精度・収束・計算時間のバランスを評価して、次の既定値を採用した。**

| 用途・C++定数 | 変更前 | 採用値 | 選んだ理由 |
| --- | ---: | ---: | --- |
| 単独GMRES：`DEFAULT_RELATIVE_TOLERANCE_GMRES` | `0` | **`1e-12`** | 真値精度の損失を小さく抑え、十分小さい残差で停止する |
| 固有値：`DEFAULT_RELATIVE_TOLERANCE_EIGEN_SOLVER` | `8e-9` | **`1e-6`** | 過度に厳しい判定を避け、固有値・固有ベクトルの成功数を増やす |
| 固有ベクトル：`DEFAULT_EIGENVECTOR_RELATIVE_TOLERANCE` | `3.2e-6` | **`4e-6`** | 必要精度内で収束しやすくし、前回候補`4.8e-6`の精度悪化を抑える |
| 逆反復内のGMRES：`DEFAULT_INNER_GMRES_RELATIVE_TOLERANCE` | `5e-3` | **`1e-3`** | 内側の解を少し正確にし、固有ベクトルの失敗を減らす |

すべてfloat/double共通の定数で、既存の公開メンバーによる個別調整もできる。変更箇所は[GMRES](../base_matrix/base_matrix_gmres.hpp)と[固有値ソルバー](../base_matrix/base_matrix_eigen_solver.hpp)の既定値である。アルゴリズム、テンプレート構造、反復上限は変更していない。

breakdown係数`8e-12`、逆反復シフト`3e-4`、絶対許容誤差、除算保護しきい値も維持した。これらは収束許容誤差とは役割が異なる。

**旧GMRES APIの`decay_rate=0`の使い方は維持される。** `base_matrix_inverse.hpp`の17箇所は引数`decay_rate`を明示設定するため、新しいソルバーの既定値を上書きする。変更が適用されるのは、直接`GmresSolver`を使い、相対許容誤差を設定しない呼出しである。

採用値は全入力・最悪誤差を保証する値ではない。固有値の追加検証では新たな失敗も残った。それも含めた比較を以下に示す。

## 2. 機械イプシロンより良くも悪くもなる、という理解でよいか

**その理解でよい。** ただし、「固定値にすること」と「許容誤差を小さくすること」は分けて考える必要がある。機械イプシロンは型の表現精度に関する値であり、アルゴリズムに要求する解の精度そのものではない。

| 許容誤差 | 旧式 | floatでの概算 | doubleでの概算 | 今回の採用値 |
| --- | --- | ---: | ---: | ---: |
| 固有値 | `8 * epsilon` | `9.54e-7` | `1.78e-15` | `1e-6` |
| 固有ベクトル | `32 * epsilon` | `3.81e-6` | `7.11e-15` | `4e-6` |
| 内部GMRES | `16 * sqrt(epsilon)` | `5.52e-3` | `2.38e-7` | `1e-3` |

今回の値は旧float設定には比較的近く、旧double設定よりは緩い。すべての値を機械イプシロンより小さくしたわけではない。なお、**単独GMRESの相対許容誤差は旧実装でも0であり、機械イプシロンを使っていたのはbreakdown判定の方だった。**

許容誤差を小さくすると通常は停止判定が厳しくなる。しかし、丸め誤差のある計算を長く続けても精度が一律に向上するとは限らない。今回の固有値ソルバーでは、許容誤差が固有値の出力順に影響し、逆反復の初期ベクトルとの組合せによって結果が変わるケースも確認した。

例として、float・8次三重対角行列では調整で固有ベクトル残差が`7.85e-2 → 1.02e-6`へ改善した。一方、7次では`7.74e-7 → 1.21e-1`に悪化した。「より小さい値」「機械イプシロン由来の値」のどちらにも、一律に最良となる保証はない。

## 3. テンプレート版とfor版の機械語を実際に数えた結果

### 3.1 数え方

同じ本体・入力・パラメータで、テンプレート版と`BASE_MATRIX_USE_FOR_LOOP_OPERATION_`を定義したfor版をビルドした。行列ベクトル積8ケース、ノルム8ケース、GMRES4ケースの計20ケース。8/16次、float/double、行列積とノルムでは実数/複素数を含む。

Linux x86-64、g++ 15.2.0、C++11、`-O2`。本体は`6b1d627`の隔離コピーで固定し、今回の定数変更と混ぜていない。GMRESは両版ともτ=0、`K=N, cycles=1, passes=1`とした。

逆アセンブルと`PTRACE_SINGLESTEP`を使い、対象区間と呼出し先で**実際に実行した浮動小数点の加算・減算・乗算・除算命令**を数えた。入力生成・printfは対象外。通常実行と追跡実行、TMP版とfor版の入出力は、全20ケースでbit単位で一致した。

| 指標 | 意味 |
| --- | --- |
| 命令の箇所数 | 実際に通った四則命令の異なるアドレス数。同じ命令を何回実行しても1箇所 |
| 命令の実行数 | ループで同じ命令を繰り返す分も数えた回数 |
| SIMD lane換算 | 1命令で複数の値を計算する分を数えた回数。未利用・重複laneの計算も含む |

箇所数は、実行ファイル全体の未使用コードまで含めた静的総数ではない。整数・アドレス・ビット演算、比較、分岐、call/returnは浮動小数点四則演算と別集計にした。今回FMAは出現しなかった。

### 3.2 四則演算命令は同じか、減っているか

**20ケース中16ケースは同じだった。複素行列積の4ケースでは、テンプレート版の四則演算命令の実行数が多かった。** 「機械語の四則演算命令数が必ず同じか減る」とは言えない。

代表例。表はすべて **for版 → テンプレート版** の順である。

| 処理 | 四則命令の箇所数 | 四則命令の実行数 | SIMD lane換算 |
| --- | ---: | ---: | ---: |
| 実数double、8次行列積 | 2 → 128 | **128 → 128** | 128 → 128 |
| 複素double、8次行列積 | 5 → 512 | **320 → 512** | 640 → 512 |
| 複素double、16次行列積 | 5 → 2039 | **1280 → 2039** | 2560 → 2048 |
| 複素double、16次ノルム | 23 → 113 | **113 → 113** | 113 → 113 |
| double、8次GMRES | 85 → 232 | **3981 → 3981** | 4565 → 4565 |
| double、16次GMRES | 85 → 640 | **22757 → 22757** | 27125 → 27125 |

実数8次行列積の内訳は、両版とも加算64回・乗算64回。for版では2箇所の命令を繰り返し、テンプレート版では展開された128箇所を通る。同じ計算量でも、並んでいる命令数は増える。

複素8次行列積では、for版がpacked SIMDを使い、複数の計算を1命令で処理している。テンプレート版は主にscalar命令となり、命令の実行数は増える。一方、全laneの演算数はテンプレート版の方が少ない。**数式上の計算量、機械語命令の実行数、SIMDの並列処理数は同じ指標ではない。**

[全40追跡の回数・内訳・再実行手順](../test_vs/algorithm_improvements/results/convergence_tolerance_tuning/instruction_counts/README.md)に原記録を保存した。専用host probeでの比較であり、以前のRAM測定バイナリそのものの命令回数ではない。マイコン向けの命令数・速度も、このx86-64の結果からは断定しない。

SIMDの採用条件、テンプレート展開で採用・見送りになった箇所、使用を保証できる範囲は、[テンプレート展開とSIMDの採用条件](13_simd_vectorization_notes.md)にまとめた。

### 3.3 四則演算が同じでもRAMが増える理由

配列容量が同じでも、コンパイラが生成する途中値の保存領域や、関数をインライン化する範囲は変わり得る。`inline`指定も全呼出しのインライン化を保証しない。[GCCの説明](https://gcc.gnu.org/onlinedocs/gcc/Inline.html)

`879a319 → b599e84`の前回比較では、GMRES double8の`_solve`フレームが480→560 byteとなり、Eigen complex double16には途中の和をスタックへ保存・再読込みする命令が現れた。四則演算を余分に実行した分のRAMを確保している、という関係ではない。[命令列とフレームの照合](../test_vs/algorithm_improvements/results/convergence_tolerance_tuning/codegen/assembly_notes.md)

前回の「最大400 byte増」は**スタックの書込み水位の差**である。その例の最大既知フレーム列の差は136 byteだった。予約していても書き込まない領域があるため、固定配列量・予約領域・書込み水位を同じ値として扱わない。

## 4. バランスの評価方法

今回は、独立した固定精度基準で解を評価し、収束状態、大きく誤った解の件数、以前の成功例を失う程度を確認した。同程度の品質の候補では、反復数と実時間も考慮した。

| 対象 | 設定値を変えても維持した精度基準 |
| --- | --- |
| GMRES | 格納A・bをDecimal80桁で解き、120桁と照合。相対前進誤差はfloat `1e-6`、double `1e-12`以内。両型`1e-6`の別集計も保存 |
| 固有値・固有ベクトル | NumPyの独立固有値との対応誤差を行列のFrobeniusノルムで正規化し、`2e-6`以内。固有対残差 `‖Av−λv‖₂/(‖A‖F ‖v‖₂)` も`2e-6`以内 |

固有値では精度と収束フラグの両方を満たすものを「成功」とした。実数・複素数APIに同じ入力を与えた重複を除いた集計も行った。固有ベクトルは符号・スケールが任意なので直接の成分一致では評価していない。重複固有値の全固有ベクトルの線形独立性まで保証する試験でもない。

候補ごとに精度基準を緩めたり、反復上限を増やしたりしていない。一般固有値は3次QR128、それ以外QR64、逆反復30、内部GMRESは`K=N, cycles=1, passes=1`、Jacobiは10 sweep。除算保護は単独GMRES`1e-25`、固有値`1e-20`。実際のクラス既定予算も使う回帰試験は別途実行した。

## 5. 固有値の採用値を選んだ根拠

### 5.1 精度・成功数

前回の探索92件と追加検証48件を、今回は140件の選定集合とした。この140件を「未使用の検証集合」とは呼ばない。固定値30組と旧ε由来の2設定を比較し、候補決定後に新しい6/10/14次の48件を検証した。

| 設定 | 選定140件：精度合格 / 成功 | 新次数48件：精度合格 / 成功 | 全188件：精度合格 / 成功 |
| --- | ---: | ---: | ---: |
| 旧ε由来の許容誤差だけを再現 | 121 / 73 | 42 / 21 | 163 / 94 |
| 変更前A：`8e-9 / 3.2e-6 / 5e-3` | 118 / 112 | 44 / 42 | 162 / 154 |
| 前回候補：`1e-6 / 4.8e-6 / 1e-3` | 122 / 122 | 40 / 40 | 162 / 162 |
| **今回採用：`1e-6 / 4e-6 / 1e-3`** | **126 / 126** | **40 / 40** | **166 / 166** |

旧ε比較は同じ現行コアに`8ε / 32ε / 16√ε`を設定し、βとシフトは固定したもの。旧コミット全体の比較ではない。βとシフトも旧式へ戻した別比較では、全188件の精度合格163・成功95だった。

採用値では、変更前Aに比べ全体の成功数が154→166になった。APIの重複を除いても、全APIが成功する入力は72/90→78/90。固有対残差`1e-3`超の入力は12/90→10/90だった。

前回候補のvtol=`4.8e-6`では5次非正規行列が残差約`2.31e-6`で止まっていた。今回の`4e-6`ではさらに計算し、約`1.09e-6`まで下がる。rtol近傍と内部GMRESの`1e-4 / 1e-3 / 2e-3`も比較し、成功数と実時間を踏まえて中間の`1e-3`を選んだ。

**悪化も残っている。** 新次数だけでは成功が42→40に減った。7次三重対角の残差は約`0.121`、14次三重対角は約`0.0425`となる失敗がある。また全体の最大残差も`0.327 → 0.502`で改善していない。この最大値の例は変更前後とも未収束である。今回の採用は成功数を増やす既定値の選定であり、最悪誤差の改善や全入力の成功を主張するものではない。

### 5.2 計算時間

選定140件を同じ実行ファイルに設定値を与えて7組ずつ計時した。CPU固定・順序交替・直列実行とし、他のコンパイルや命令追跡は停止した。solverの構築から全求解までを測り、前の解を再利用しない。

一般実数版・floatの代表例。時間は各設定の中央値、時間比は組ごとの比の中央値なので単純な商とは少し異なる。

| 入力 | 変更前A → 採用値 μs | 時間比 | 成功状態 |
| --- | ---: | ---: | --- |
| 8次三重対角 | 38.874 → 28.331 | 0.736 | 不成功→成功 |
| 16次三重対角 | 333.010 → 260.174 | 0.779 | 不成功→成功 |
| 5次非正規 | 10.381 → 10.390 | 0.996 | 両方成功 |
| 7次三重対角 | 21.322 → 35.880 | 1.796 | 成功→不成功 |

140ケースを同じ回数ずつ使う参考集計では、中央値時間の合計比は0.970。ケースごとの時間比中央値は0.996だった。一方、両方成功した108ケースに限ると時間合計比は1.029で、全成功ケースが一律に速くなったとは言えない。精度と成功数の改善を主な利点とし、局所的な速度改善・悪化の両方を含めて採用した。

[固有値の全探索・旧ε比較・新次数検証・時間結果](../test_vs/algorithm_improvements/results/balanced_tolerance_selection/eigen/README.md)を参照。

## 6. 単独GMRESに`1e-12`を選んだ根拠

4/8/16次、float/double、良条件・Hilbert・列スケール行列、6通りのGMRES設定について、108設定×2右辺状態を比較した。上限不足や悪条件によって変更前から不合格の設定も含む。

| τ | 型別精度の合格 / 216状態 | 両型`1e-6`の合格 / 216状態 | 反復数合計 | 参考時間合計比 |
| --- | ---: | ---: | ---: | ---: |
| 変更前`0` | 94 | 104 | 2669 | 1.000 |
| **採用`1e-12`** | **90** | **102** | **2286** | **0.816** |
| `1e-10` | 72 | 100 | 2127 | 0.748 |
| `1e-7` | 64 | 96 | 1682 | 0.582 |
| `1e-6` | 58 | 88 | 1415 | 0.498 |

型別精度はfloat `1e-6`、double `1e-12`。採用値で合格を失った4状態の最大相対前進誤差は`2.568e-12`だった。`1e-10`では失う状態が22に増え、その最大誤差も`2.906e-8`になる。緩い設定は速くなるが、既定値としての精度損失が大きいため採用しなかった。

時間合計比は108設定を同じ回数使うと仮定した参考値で、全利用で約18%速くなるという意味ではない。設定別時間比の中央値は0.994で、効果の大きい設定は偏っている。

追加の2次行列 `A=[[1,0],[δ,δ]], b=[1,0]` では、δ=`2e-10`の真値`[1,-1]`を採用値でも両型で2反復で維持した。τ=`1e-7`では1反復で止まり、前進誤差が約0.707となるため、この例も保守的な`1e-12`を選ぶ根拠とした。

δ=`2e-14`ではbreakdown係数の影響で、元から正確な解を得られない。採用値では小さい残差によって状態がbreakdownからconvergedへ変わるが、前進誤差約0.707は改善しない。収束フラグだけで解の正しさを保証しない点は変わらない。[選定表・旧API監査](../test_vs/algorithm_improvements/results/convergence_tolerance_tuning/balanced_defaults/gmres/balanced_gmres_decision.md)

## 7. 採用後のRAM・ビルド検証

定数変更前後を同じRAM probe・コンパイル条件で再ビルドし、TMP56ケース＋for56ケースを比較した。**全112比較でsolverの`sizeof`、入力・出力を含む固定領域、観測スタック書込み水位、最大既知フレーム列は不変だった。** 今回の既定値変更の前後比較であり、以前のテンプレート展開による増加が消えたという意味ではない。[RAM再確認の記録](../test_vs/algorithm_improvements/results/balanced_tolerance_selection/memory/README.md)

新しい8次三重対角の回帰試験では、実際のコンストラクタ既定値のまま、解析的な固有値と独立固有対残差を確認する。既存の精度assertは緩めていない。

検証はC++11、TMP/for、既定数学/ホスト標準数学、禁止ヘッダ・例外なし構成、ASan/UBSan/浮動小数点ゼロ除算検査、既存の8ビルド構成を対象とし、**全24実行が成功した**。[検証結果とソースhash](../test_vs/algorithm_improvements/results/balanced_tolerance_selection/validation/validation.json)を保存した。マイコン実機の速度、割込み込みの最悪スタック、WCETは未測定である。
