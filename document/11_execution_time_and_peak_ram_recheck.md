# 前回測定からの実行時間・RAMの再評価

評価日：2026-11-17

## 1. 結論

**実行時間・RAMともに悪化例があり、「前回から悪化していない」とは判断できない。** また、今回追加した固有値の入力では、現在の固定パラメータによる解の品質の悪化も確認した。

| 対象 | 今回確認した変化 |
| --- | --- |
| GMRES | float・16次Hilbert行列で約2.2倍。明示的な再始動設定では約4.2倍。breakdownによる停止が減り、実反復数が増加 |
| 一般固有値 | 既定しきい値のfloat・8次対称行列で全求解時間が約29%増加。固有ベクトル残差も `4.65e-7 → 7.85e-2` に悪化 |
| RAM | solverの`sizeof`は不変だが、テンプレート構成の56処理中14処理で観測したスタック使用量が増加。最大増加は400 byte |
| QR・LU・Cholesky | 今回の比較で明確な時間増加・観測RAM増加なし。該当benchmarkの実行コードと定数データも前回版と完全一致 |

主要な時間増加は直近の固定パラメータ化、主要なスタック増加はそれ以前のテンプレート展開とコード生成の変更に対応する。固定値を導入した際の回帰試験32実行の成功は、この追加した入力集合での性能・精度を保証していなかった。

今回は調査用コードと記録を追加し、本体・サブモジュールの実装は変更していない。

## 2. 比較元の特定

| 呼称 | commit | 目的 |
| --- | --- | --- |
| 前回版 | `879a31981d4cb99173939bd4a12df96bf8ccdf1a` | 最後の保存済み同条件時間比較の改善後 |
| 固定値導入直前 | `ab31b0d` | テンプレート展開などと固定値化の影響を切り分ける |

前回のメタデータ・ソースhashとGit履歴を照合して前回版を特定した。数学・utilityのサブモジュールは3版で同一。既存5種類のbenchmarkソースも前回記録と同じ内容である。比較元の根拠は[照合記録](../test_vs/algorithm_improvements/results/performance_recheck_2026_11_17/baseline_notes.md)を参照。

以前のRAM記録は2026-11-10の`sizeof`と関数単位の`.su`が中心で、呼出し全体のピークを直接測ったものではなかった。また、その時点の一部ヘッダは保存hashと一致するGit版が存在しない。したがって、古い`.su`と今回の動的なスタック測定を単純に引き算せず、再現可能な前回版と現行版を同じ測定方法で比較した。

## 3. 測定条件と判定方法

- Linux x86-64、g++ 15.2.0、C++11、`-O2 -Wall -Wextra -Werror`、固定配列、既定の数学ライブラリ。`-ffast-math`は使用しない。
- 3版ともGitから隔離展開し、同じbenchmarkソースとマクロでビルド。`ALGORITHM_IMPROVEMENTS`は3版すべてで有効にした。
- 時間測定は同じ論理CPUへ固定。1回のプロセスwarm-up後、各版を順序を入れ替えながら7プロセスずつ直列実行した。コンパイル・RAM測定を同時実行していない。
- 既存benchmarkは413設定。固有値の追加probeは144設定。for構成の追加比較ではGMRESと矩形GMRESの140設定を測定した。
- 大きな遅延の抽出条件は「7組の時間比の中央値が1.10超、かつすべての組で1.05超」。小さい変化を無視してよいという精度保証や統計的有意性の定義ではなく、変動のあるホスト測定から確認対象を絞る基準である。全設定の時間比・最小最大値も保存した。

本文の時間表は各版の**7プロセスの中央値と、その中央値同士の比**を記す。CSVの`paired_ratio_median`は同じ測定組の比を先に計算した中央値なので、表の比と少し異なる。benchmark内部の反復平均・trial最小値などの集計は前回と同じまま維持した。

時間だけで評価せず、誤差、実反復数、収束状態、格納量も確認した。既存benchmarkの品質指標の意味・測定に含む処理は[監査ノート](../test_vs/algorithm_improvements/performance_benchmark_audit.md)を参照。

## 4. 実行時間

### 4.1 既存benchmarkの全体像

| benchmark | 設定数 | 明確な遅延として抽出した設定数 | 内容 |
| --- | ---: | ---: | --- |
| QR | 90 | 0 | `.text`・`.rodata`が前回版と現行版で同一 |
| LU・Cholesky | 108 | 0 | `.text`・`.rodata`が前回版と現行版で同一 |
| GMRES | 126 | 4 | float・16次Hilbert、直交化1回に集中 |
| 矩形GMRES | 14 | 1 | double・128×4の既存矩形API |
| 固有値 | 75 | 4 | double・4/16次の厳しい逆反復設定 |

コードが同一でも計時値はOS負荷・周波数などで変動する。QR・LU・Choleskyは今回のソース変更による実行コードの悪化を認めず、RAM専用probeでも増加を観測しなかった。

### 4.2 GMRES：停止条件の変化で実反復数が増える

floatの16次Hilbert行列、直交化1回、相対・絶対収束許容誤差0での比較：

| 設定 | 前回時間 μs | 現行時間 μs | 時間比 | 実反復数 前回→現行 |
| --- | ---: | ---: | ---: | ---: |
| `K=16, cycles=1`、前処理なし | 2.319 | 5.103 | 2.20倍 | 7 → 16 |
| `K=8, cycles=4`、前処理なし | 2.225 | 9.348 | 4.20倍 | 7 → 32 |
| `K=8, cycles=4`、逆対角前処理あり | 2.567 | 9.327 | 3.63倍 | 8 → 32 |

前回版・固定値導入直前のfloatではβが約`9.54e-7`、現行版では`8e-12`。1000試行すべてで、以前はbreakdownにより止まっていたものが、現行では設定した反復上限まで進んだ。主要な遅延は固定値化の前後で発生している。

**最大反復回数を増やしたわけではない。** `K=16, cycles=1`は両版とも最大16回。表の最大32回は、両版に明示指定した`K=8, cycles=4`の設定であり、既定GMRESの上限ではない。

長く計算すれば必ず解が良くなるわけでもない。最終の格納済みA・b・xからlong doubleで再計算した相対実残差は次のとおり。

| 設定 | 前回の相対実残差 | 現行の相対実残差 |
| --- | ---: | ---: |
| `K=16, cycles=1`、前処理なし | `8.84e-8` | `9.23e-8` |
| `K=8, cycles=4`、前処理なし | `8.84e-8` | `5.46e-8` |
| `K=8, cycles=4`、前処理あり | `9.85e-8` | `5.84e-8` |

full Kでは時間・実残差とも悪化した。再始動では時間を使って残差を減らす交換関係になっている。収束許容誤差0のため、これらは両版とも収束フラグがfalseであり、フラグだけで解の品質を評価していない。

既存CSVの`rms_target_error`は製造した目標ベクトルとの差で、丸められた悪条件A・bの厳密な解への誤差ではない。これを真の前進誤差と読み替えて「精度が何倍悪化」とは結論しない。

### 4.3 矩形GMRES：テンプレート構成の影響

double・128×4の`gmres_k_rect`は、テンプレート構成で1.333 → 1.754 μs（約32%増）だった。解の誤差は同じで、この遅延は固定値導入直前にも現れている。

同じ前後比較を`BASE_MATRIX_USE_FOR_LOOP_OPERATION_`有効で行うと、1.316 → 1.324 μs（約0.6%増）となり、明確な遅延の抽出条件を満たさなかった。GMRES・矩形GMRESの全140設定で、for版とテンプレート版の数値出力・オブジェクトサイズは一致した。

このケースはテンプレート展開とコード生成の影響が強く疑われる。キャッシュやレジスタ使用量のどれが主因かまでは特定していない。for版でもHilbertの反復数増加による遅延は残るため、ループ方式を変えるだけで全遅延は解消しない。

### 4.4 固有値：既存の厳密設定にも増加がある

既存benchmarkの`inverse_strict_p1`では、double・4次が9.275 → 13.168 μs、16次が377.744 → 505.317 μsとなった。直交化2回でも同様の増加があった。

この設定は固有ベクトル許容誤差と内部GMRES許容誤差を明示する一方、シフトは各版の既定値を使う。したがって完全に同じパラメータでの比較ではない。シフト変更後の誤差も増え、現行の既定値を使う全求解については、次節の補助probeで別途確認した。

## 5. 追加の固有値試験で見つかった品質の悪化

入力を格納精度にかかわらず厳密に表現できる三重対角行列（対角2、隣接要素-1）と、その対角相似変換にした。固有値の真値を独立に求め、固有対残差もlong doubleで計算した。一般実数・複素数、float/double、4/8/16次、既定値・明示A・明示B、値のみ・全求解の144設定で比較した。

この節の「既定値」はしきい値を指す。予算は全版・全profileでQR64、逆反復30、内部GMRES `K=N, cycles=1, passes=1`に揃え、`division_min=1e-20`、絶対許容誤差0とした。QR予算はクラスの初期値`10*N`そのものではない。以下の代表例はすべて64 sweep未満で固有値が収束している。

既定しきい値の一般実数・対称入力・floatの結果：

| 次数 | 時間 μs 前回→現行 | 固有対残差 前回→現行 | ベクトル収束 前回→現行 | QR sweep 前回→現行 |
| --- | ---: | ---: | --- | ---: |
| 8 | 30.124 → 38.765 | `4.649e-7 → 7.845e-2` | true → false | 13 → 15 |
| 16 | 258.332 → 334.767 | `7.630e-7 → 7.807e-7` | true → false | 30 → 33 |

8次では一般複素数版でも同じ残差悪化が発生した。16次は残差自体が小さいまま収束フラグが変わる例であり、8次の大きな品質悪化と区別する。

前回版にも候補Aの公開パラメータ4個を指定すると、この入力の数値結果・フラグは現行版と一致した。さらに現行版のAから1係数だけを以前のfloat既定値へ戻す診断を行った。

| 差し戻した係数 | 8次floatの固有対残差 | ベクトル収束 |
| --- | ---: | --- |
| なし（現行A） | `7.845e-2` | false |
| 固有値rtolのみ：`8e-9 → 9.536743e-7` | `4.425e-7` | true |
| vtolのみ | `7.845e-2` | false |
| シフトのみ | `7.845e-2` | false |
| 内部GMRES許容誤差のみ | `7.845e-2` | false |

rtolを変えると固有値の出力順が変わり、逆反復の初期ベクトル`ones + e_slot`と組み合わさる固有モードも変化した。現行Aの順序では、厳密な固有モードへの初期ベクトルの射影が0となる組が1個あり、旧rtolの順序では0個だった。これは初期ベクトルと入力の対称性による零射影の問題と整合する。有限精度の全過程でその射影が厳密に0のままという証明ではないが、rtolだけの変更で悪化・解消を再現できた。

前回の候補Aの探索は主に3次行列を使っていた。今回の8次入力はその範囲外であり、候補Aを全入力へ適用する際の弱点が明らかになった。**固有値許容誤差を厳しくしても、固有ベクトルまで一律に良くなるとは限らない。**

[固有値の詳細分析・差し戻し診断](../test_vs/algorithm_improvements/results/performance_recheck_2026_11_17/eigen_analysis.md)に、改善したケースも含めて記録した。

## 6. 呼出し先を含むRAM比較

### 6.1 測定する領域を分ける

solver・入力・出力を保持する呼出し元の固定領域を`context`として測り、演算中の呼出し先を含むスタックの書込み深さを専用スタック上で測定した。演算内部への計測hookは入れていない。2種類のpaint値×3回の最大値を採用し、空関数と入れ子の既知バッファで校正した。

同じバイナリについてGCCの`.su`とcall graphも取得し、到達可能な最大既知フレーム列を集計した。未解決の`memmove`などを隠して上限と扱わない。

`context + 観測スタック`はこの入力で必要だったRAMの指標である。書き込まれない予約領域や、別入力・割込み・MCUのABIを含む最悪ピークRAMの保証ではない。`sizeof(solver)`はcontextに含まれるため二重加算しない。

### 6.2 増加例

float/double、8/16次、14処理の56ケースを3版・2ループ構成で比較した。以下は通常のテンプレート構成の代表例。単位はbyte。

| 処理 | context（不変） | 観測スタック 前回→現行 | 合計 前回→現行 | 増加 |
| --- | ---: | ---: | ---: | ---: |
| GMRES full、double、8次 | 1,912 | 616 → 688 | 2,528 → 2,600 | +72（2.85%） |
| GMRES restart、double、16次 | 4,152 | 856 → 912 | 5,008 → 5,064 | +56（1.12%） |
| Eigen complex、float、16次 | 5,344 | 7,160 → 7,368 | 12,504 → 12,712 | +208（1.66%） |
| Eigen complex、double、16次 | 10,624 | 13,928 → 14,328 | 24,552 → 24,952 | +400（1.63%） |

- solverとcontextの`sizeof`は全56ケースで不変。
- テンプレート構成では14ケースが8〜400 byte増加、42ケースが不変。
- 最大絶対増加は400 byte、context込みの最大増加率は約2.85%。
- 最大400 byteの増加は固定値化直前にも存在した。固定値化による追加の観測差は、テンプレート構成でEigen complex double8の16 byte。
- for構成は前回版→固定値導入直前で全56ケース不変。現行版ではEigen complex float8だけ16 byte増加し、55ケースは不変。

スタック増加の大部分がテンプレート構成に集中し、固定値化前に発生しているため、テンプレート展開に伴うインライン化・フレーム構成の変化が主因と考えられる。反復数を増やしても通常は同じ作業領域を再利用するので、反復数をRAMへ掛け算してはいない。

[RAMの全結果と測定方法](../test_vs/algorithm_improvements/results/performance_recheck_2026_11_17/memory/README.md)には全14増加例、各フレーム、解析できなかった外部呼出し、校正結果を保存した。

## 7. 採用判断で見直す点

1. **固有ベクトルの失敗ケースを先に扱う。** 3次だけでなく今回の8次・16次を検証集合へ加え、決定的な初期ベクトルと固有値の出力順の組合せを再評価する必要がある。rtolだけの局所的な差し戻しで全入力が解決するとは判断しない。
2. **GMRESのβ・収束許容誤差を組合せで評価する。** 小さいβで正しい探索方向を残せた前回の例と、今回の悪条件入力で実反復数が増えた例を両方含める。固定値の独立設定は可能だが、全用途で単一の小さいβが有利という結果にはなっていない。
3. **テンプレート展開のRAM・時間を関数単位で評価する。** for構成は今回のスタック増の大部分と矩形GMRESの遅延を避けられた。一方、GMRES全体の高速化まで一律に保証するものではないため、処理ごとの選択が必要になる。

今回の再評価はホスト上の比較であり、マイコン実機の命令時間、割込み込みの最大スタック、WCETは未測定である。
