# 再測定の比較元と保存記録の対応

2026-11-17、現在のcommit `b599e84` に対する比較元を、保存メタデータ、SHA-256、Git履歴から確認した。個々のファイルの期待hash・実測hashは [baseline_audit.json](baseline_audit.json) に保存した。

## 最後の時間測定に対応する版

最後の保存済み同条件時間比較の改善後は **`879a31981d4cb99173939bd4a12df96bf8ccdf1a`**。2026-11-12の `timing_environment.json` が比較前 `f50060e`、比較後 `879a319` を明記している。今回の比較主軸には、この `879a319` と `b599e84` を同じ条件で再ビルド・再測定する方法を使える。

- 2026-11-12の記録にある `base_matrix_gmres.hpp`、`base_matrix_inverse.hpp`、`base_matrix_numerical.hpp` の3件は、`879a319` の内容とSHA-256が完全一致した。
- 数学・utilityのgitlinkは `879a319` と `b599e84` で同じ。数学は `2a2c19b91e9dfe69de532abebbcbdd25f8fbbd5e`、utilityは `6d4807de5eb5bfbad8bff950caf3fd20757a9b30`。
- 現在の5種類のbenchmarkソースは、2026-11-11に記録された同名ファイルのhashとすべて一致した。GMRESソースは2026-11-12の記録とも一致する。当時はbenchmarkがGit未追跡だったため、`879a319` のヘッダと現在の同一内容のbenchmarkを組み合わせて再現する。
- `/tmp/matrix_root_policy_timing_4et38633` に残っていた4種類×前後×5回の時間CSVを [historical_timing](historical_timing/README.md) に保存した。GMRES10件と環境JSONは、既存のリポジトリ保存版とバイト単位で一致した。残る3種類のCSVも同じ元ディレクトリから回収したが、独立のリポジトリ保存版との照合ではない。

2026-11-11の `public_roots` は、README自身が同条件の時間比較としては扱わないと明記している。その23件の行列ヘッダhashは `879a319` と21件一致し、GMRES・QRの2件は一致しない。この2件の記録hashに一致する版は、利用可能なGit全履歴の同名ファイルには見つからなかった。したがって、11/11の作業途中の記録を `879a319` の完全なスナップショットとは扱わない。

## 以前のRAM記録に対応する版

保存された `results/*_benchmark_*.su` は2026-11-10の統合評価によるものであり、最後の11/12時間測定と同時に取得されたものではない。

2026-11-10の `source_hashes.json` と比較すると、`f6950f3` と `f50060e` の `base_matrix` ツリーは完全に同一で、記録された23件中19件のヘッダが一致した。

| 対象 | `f6950f3` / `f50060e` と記録hashの一致 |
| --- | --- |
| GMRES、inverse、numerical、vector、matrix、complex等の19件 | 完全一致 |
| QR、LU、Cholesky、Eigenの4件 | 不一致 |

不一致4件の記録hashに一致する版は、利用可能なGit全履歴の同名ファイルには見つからなかった。改行形式を変えただけの差でも一致しなかった。この4件を同一実装・同一測定ソースと断定できないため、`f50060e` の全体測定を「11/10の完全再現」とは呼べない。GMRESの中核3ヘッダについては完全一致する旧版として追加比較に使用できる。

さらに11/10のutilityヘッダには、後に復元された未commitの変更が含まれていた。`/tmp/base_utility_restore_b_ksipuz/base_utility/base_utility.hpp` に記録hashと完全一致するバックアップが残っているが、サブモジュールcommitを取得するだけではこの作業状態を再現できない。古いQR・LU/Choleskyのbenchmarkにも、公開平方根APIへの移行前後でソース変更がある。以上から、初期RAM記録全体の完全な再ビルドを現存のGit commitだけで保証することはできない。

## RAM数値の限界

- `sizeof` はソルバが保持する領域であり、入力、出力、呼出し先の局所変数を含まない。
- `.su` はコンパイラが報告する関数ごとのフレームである。呼出し先の同時生存領域、共有済みの呼出し側領域、インライン化を区別する必要があり、単純加算も単体最大値もそのままピークにはならない。
- 11/12の時間記録には `.su` がなく、その版との呼出し全体の比較には新たな測定が必要である。
- 旧記録には呼出し全体の動的なピークRAM測定がない。今回の呼出し全体の測定と、旧 `.su` の単体フレーム値は区別する。
- ホスト測定はMCUのABI、割込み、RTOS、ライブラリ実装を含む最大RAMやWCETの保証ではない。

今回の性能判断は、新しい同条件比較を主とし、回収した古い時間と `.su` は測定履歴・個別の参考値として扱う。
