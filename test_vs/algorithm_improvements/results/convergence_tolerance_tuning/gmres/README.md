# GMRES: 収束許容誤差だけを調整する調査

**用途を限定すると、固定した解の品質基準を満たしながら時間を短縮できた。ただし、全入力に共通する正の許容値への変更は支持できない。** 本体の既定値`relative_tolerance=0`は変更していない。

今回のwell行列群では、floatの`tau=1e-6`、doubleの`tau=1e-12`が有効だった。悪条件行列で時間が元に戻っても、真値との誤差が大きい例は採用候補として扱わない。

## 比較条件

- 調整対象: `GmresSolver::relative_tolerance`のみ。`absolute_tolerance=0`、`division_min=1e-25`、現在のbreakdown係数`8e-12`を固定。K、cycles、直交化回数、前処理も各設定で固定。
- 現在: `6b1d627edf2de6e3e56deca59b83b37e942a97aa`。本体headersは前回再測定のb599e84と同じ。
- 前回比較元: `879a31981d4cb99173939bd4a12df96bf8ccdf1a`、tau=0。現在版tau=0も別に比較し、しきい値調整の効果と版間差を分けた。
- C++11、g++ 15.2.0、`-O2`、既定数学、テンプレート演算、固定配列。各commitのsubmoduleをそのまま使用。
- tau: `0, 1e-12, 1e-10, 1e-9, 1e-8, 3e-8, 1e-7, 3e-7, 1e-6, 3e-6`。
- 元の`gmres_benchmark.cpp`の108設定: float/double、N=4/8/16、well/Hilbert/列スケール行列、6種類のK/cycles/passes/前処理。各設定は前回と同じ1000回のRHS加減算を行い、繰り返される2状態それぞれの解を評価した。
- 追加反例: `A=[[1,0],[delta,delta]], b=[1,0]`、真値`[1,-1]`、delta=`2e-6, 2e-10, 2e-14`、float/double。

### 品質基準をtauに合わせて緩めない

格納されたA・b・解を16進浮動小数で出力し、Decimal80桁の独立解法で真値を求め、120桁で照合した。相対前進誤差は`||x-x_true||₂ / ||x_true||₂`。残差もDecimalでA・b・xから直接計算した。Hilbertの真値は製造時の全要素1というベクトルではなく、**丸めて格納されたA・bの厳密な解**である。

評価には次の固定した2基準を使い、tauを変えても変えない。

| 評価profile | floatの相対前進誤差 | doubleの相対前進誤差 |
| --- | ---: | ---: |
| `typed` | ≤1e-6 | ≤1e-12 |
| `engineering` | ≤1e-6 | ≤1e-6 |

これらは比較用に明示した品質目標であり、すべての利用側へ強制する精度ではない。以下の推奨候補は`typed`基準を使い、さらに両RHS状態で`converged=true`、`breakdown=false`、独立残差も指定tau以下であることを確認した。

全2442状態、41種類の異なる格納入力を評価した。非有限出力なし、反復上限K×cyclesの違反なし、保持オブジェクトの大きさも不変だった。固定K/cyclesの不足によりtau=0から品質不合格の設定もあるため、「18設定すべて成功」とは扱わない。

## 時間と品質を両立できた用途別候補

well行列群は各型18設定、各設定2状態。表の対象は両状態で固定品質を満たす設定に限定し、tau=0で合格していた設定の合格を失っていないことを確認した。

| 用途 | tau | 品質・状態を満たす設定 | 最大相対前進誤差 | 現在tau=0比の時間比 | 879tau=0比の時間比 |
| --- | ---: | ---: | ---: | ---: | ---: |
| well、float、1e-6品質 | 1e-6 | 16/18 | 7.259e-7 | 0.512 | 0.459 |
| well、double、1e-12品質 | 1e-12 | 13/18 | 8.115e-13 | 0.637 | 0.573 |

時間比は「7プロセスの対比較中央値」を各設定で求め、その設定間中央値を示したもの。全設定・全測定組で同じ短縮率になる意味ではない。個別設定の比の範囲は`timing/summary.csv`に保存した。前者16設定のうち14設定、後者13設定のうち9設定では、現在tau=0との全7組で短縮した。

対応するwell群全体の2状態合計反復数は、floatで400→164、doubleで436→270。品質合格の状態だけではfloatが388→152、doubleが376→210となる。解の誤差そのものが常に以前以下という主張ではなく、**事前に固定した精度要求内で時間を削減する選択**である。

floatのtau=1e-7でも前進誤差の合格32状態を維持し、最大誤差1.583e-7、合格16設定の時間比中央値は現在tau=0比0.652だった。ただし32状態中`converged=true`は20状態、breakdownが2状態、独立残差がtau以下は22状態で、要求した残差には未達が残った。今回のwell群で状態まで含めてそろった候補はtau=1e-6である。

## 一律変更に向かない理由

### 列スケール行列では精度を失う

doubleのtau=1e-12でも、前処理ありのN=4/K=2/C=4とN=8/K=4/C=4で、現在tau=0における1e-12品質の合格を失った。例えばN=4の一方の状態は、前進誤差`6.18e-17 → 2.57e-12`。well群で有効だった同じtauを全行列へ適用する根拠にはならない。

float全benchmarkの1e-6品質は、tau=1e-10まで46/108状態を維持し、2状態合計反復数1314→1205となった。ただし、Hilbertの遅くなった計算はほぼ残り、54設定全体の時間比中央値は現在tau=0比0.997で、全体を大きく改善する値ではない。tau=1e-9ではscaled16の前処理あり設定が`9.25e-7 → 1.19e-6`となり、品質合格2状態を失った。

### Hilbertの時間だけを戻しても採用しない

float Hilbert16、K=16/C=1/P=1の例:

| tau | 2状態の反復数 | 879tau=0比の時間比 | 2状態の相対前進誤差 |
| --- | --- | ---: | --- |
| 0 | 16 / 16 | 2.276 | 1.007 / 1.093 |
| 1e-7 | 7 / 6 | 0.853 | 0.996 / 0.997 |
| 1e-6 | 5 / 5 | 0.665 | 0.997 / 0.997 |

停止を早めれば以前より速くできるが、この例はどの値も固定した1e-6品質に達しない。float Hilbert群は全36状態が同品質に不合格で、時間短縮を「品質も満たした改善」として採用しない。doubleでも正のtauを大きくすれば、もともと合格していたHilbertの設定まで不合格になる。

### 小さな残差で大きな解の誤差を見逃す

`delta=2e-10`の反例は、現在tau=0では両型とも2反復で真値を得る。tau≥1e-9では1反復、独立相対残差約2e-10で`converged=true`となるが、相対前進誤差は約0.707。したがって、収束の許容値は入力の条件数と必要な解の精度に合わせて利用側が選ぶ必要がある。

`delta=2e-14`は、現在の固定breakdown係数8e-12によってtau=0から1反復で停止し、相対前進誤差約0.707となる。正のtauは状態を「breakdown」から「converged」へ変えても、失った方向を復元しない。879のdouble版はこの例を2反復で解けた。**breakdown係数の影響を収束許容誤差だけで解消することはできない。**

## 運用案

- ライブラリ全体の既定tau=0は維持する。普遍的な正の値を今回の結果から決めない。
- 利用側が入力範囲と必要精度を把握している場合、既存の`solver.relative_tolerance`に用途別の値を指定する。今回のwell群ではfloat1e-6 / double1e-12が候補となった。
- 代表入力だけでなく悪条件・スケール差・near-breakdownを含めて、真値との誤差、独立残差、収束・breakdown状態を同じ基準で確認する。tauの変更だけでK/cycles/passesやbreakdown係数の不足が解消するとは扱わない。

RAMについて今回直接確認したのは`sizeof(solver)+前処理ベクトル`の不変性。tauは既存の実行時メンバーに設定しており、各tauを同じ実行ファイルで測った。今回あらためてピークstackを測ったわけではない。

## 原記録と再実行

- `metadata.json`: commit、依存先、compiler、flags、probe hash。
- `*.exact.csv`: 各tauの状態、反復数、16進A/b/x。既存資料は上書きしていない。
- `quality_cases.csv`: 全2442状態のDecimal品質・状態・比較元との差。
- `quality_summary.csv`: 全tau×型×行列群の集計。
- `candidate_summary.csv`: 固定品質合格設定、および品質＋状態合格設定の時間比。
- `quality_validation.json`: 80/120桁照合、有限性、反復上限、保持量の検証。
- `timing/`: 6構成×7プロセス、各108設定の原測定、対比較比率、実行順・CPU。`validation.json`では全4536行の1000回後の反復数・状態・x[0]が品質probeの最終RHS状態と一致することを確認した。

```sh
python3 test_vs/algorithm_improvements/gmres_tolerance_sweep.py --phase explore
# 他の重い処理を停止してから、直列で時間測定する。
python3 test_vs/algorithm_improvements/gmres_tolerance_sweep.py \
  --phase timing --taus 0 1e-12 1e-10 1e-7 1e-6 --repeats 7
```

時間計測は元benchmarkと同じ1000回のRHS加減算、ゼロ初期値からの解法、volatile sinkを含む。同じ新probeを879と現在へビルドして比較しており、別バイナリで保存された過去の絶対時間をそのまま分母へ使っていない。品質探索は1000回のRHS列が2状態で繰り返すことを確認して各状態を1回ずつ解き、実際の1000 solvesによる最終値との一致を計時後にも検証した。
